# Argus — Permission-Aware Enterprise RAG Platform

> 12-week build plan. Rebuild of the lost "Secure RAG with RBAC" project, scaled from
> a single-purpose pipeline into a production-grade platform.

Working names: **Argus** (the hundred-eyed watchman), `gatekeeper-rag`, `clearance`.
Pick one and use it consistently across repo, docs, and Upwork copy.

---

## 1. Positioning

**One-line pitch:** A multi-tenant RAG platform where authorization is enforced inside the
database, retrieval quality is measured on every commit, and a red-team suite proves that
users cannot extract documents they are not cleared to see.

Why this beats the previous version as a portfolio piece:

| Old project | New project |
|---|---|
| One access model (`&&` array overlap) | ABAC + Postgres RLS + chunk-level ACLs, three enforcement layers |
| Dense vector search only | Hybrid BM25+dense, RRF, cross-encoder rerank, contextual retrieval |
| Eval script | CI-gated eval harness with published ablation table and regression thresholds |
| "It works" | "0 leaks across 250 adversarial prompts, nDCG@10 0.81, p95 1.4s, $0.004/query" |
| Flask demo | FastAPI + workers + Next.js console + MCP server + observability stack |

The three artifacts that actually sell this to a technical buyer, in order:
1. The **ablation table** (numbers proving each retrieval technique earned its place).
2. The **red-team results table** (0 leaks, with the attack corpus in the repo).
3. The **ADR folder** (10-15 decision records showing judgment, not just code).

Everything else is supporting evidence.

## 3. The four pillars

### 3.1 Security & authorization — the differentiator

Almost no portfolio RAG project does this. Go deep.

**Policy model (ABAC, not just RBAC):**
- Principal attributes: `tenant`, `groups[]`, `clearance_level`, `department`, `region`,
  `employment_type`, time-boxed grants with `valid_until`.
- Resource attributes: `sensitivity_label`, `owner_group`, `need_to_know_tags[]`,
  `jurisdiction`, `retention_class`.
- Policies expressed as data (rows in `policies`), evaluated to a SQL predicate — not
  hardcoded Python `if` statements. Ship a small policy DSL or use Cedar/OPA bindings.

**Three enforcement layers, each independently testable:**
1. **Postgres Row-Level Security.** `SET LOCAL app.principal = '<jwt claims json>'` per
   transaction; RLS policies on `documents` and `chunks`. The database itself refuses to
   return unauthorized rows — a compromised API layer still cannot leak. This is a much
   stronger claim than the old `&&` filter and is the headline of the security story.
2. **Predicate pushdown into vector search.** Naive RLS + HNSW degrades badly (the index
   scans, then rows get filtered, so top-k comes back short). Solve it properly:
   partial/partitioned HNSW indexes per tenant, `iterative_scan = relaxed_order` in
   pgvector 0.8, and an over-fetch-then-filter strategy with measured recall loss.
   **Write the benchmark for this and put it in the README** — filtered-ANN recall is a
   genuinely hard problem and demonstrating you understand it is a strong signal.
3. **Post-retrieval re-check + citation redaction.** Defense in depth; also catches
   stale-grant races.

**Chunk-level ACLs.** Chunks inherit document ACLs but can be overridden — e.g. a salary
table inside an otherwise-public handbook. Nobody does this; it's a great demo moment.

**Prompt-injection defense.** Retrieved documents are untrusted data:
- Spotlighting/delimiting of retrieved content in the prompt.
- An injection classifier on ingested chunks, flagged in the admin console.
- Architectural rule: retrieved content can never expand tool scope or principal grants.

**Hash-chained audit log.** Every query records principal, query, docs retrieved, docs
*denied*, latency, cost, answer hash. Each row chains the previous row's hash — tamper-evident.

**Red-team suite (`make redteam`).** 250+ adversarial prompts across categories:
cross-tenant exfiltration, group escalation via role-play, indirect injection planted in
documents, citation forgery, embedding-inversion probes, enumeration via denial timing.
CI fails the build if leak rate > 0. Report the two metrics that matter as a pair:
**leak rate** (0%) and **over-blocking rate** (authorized content wrongly withheld) —
reporting both shows you know the tradeoff exists.

### 3.2 Retrieval quality — the depth

Build these in order, measuring each one:
1. Baseline: fixed 1000/200 token chunks, dense-only, top-k=10.
2. **Structure-aware chunking**: heading hierarchy preserved, tables kept intact,
   sentence-boundary splits, parent-document retrieval (embed small, return large).
3. **Contextual retrieval** (Anthropic's technique): an LLM prepends 50-100 tokens of
   document context to each chunk before embedding. Typically the single largest win.
   Cache aggressively — this is your biggest token cost.
4. **Hybrid search**: BM25 + dense, combined with Reciprocal Rank Fusion.
5. **Cross-encoder rerank**: retrieve 50, rerank to 8, ONNX on CPU.
6. **Query understanding**: rewriting, multi-query expansion, HyDE, decomposition into
   sub-queries, LLM-extracted metadata filters (`"Q3 policy" → date range + doc_type`).
7. **Agentic multi-hop**: planner decides strategy, issues follow-up retrievals, with a
   hard step/token budget and full trace.
8. **Groundedness check**: post-generation verifier flags claims unsupported by cited
   spans; UI shows unsupported sentences in amber.
9. **Semantic cache** on query embeddings with a per-principal key (never cache across
   authorization boundaries — a subtle bug worth calling out in an ADR).

**Ingestion formats:** HTML (BeautifulSoup), PDF with layout (Docling), DOCX, Markdown,
CSV/XLSX, and images via OCR. Incremental re-index keyed on content hash.

### 3.3 Evaluation — the credibility

This is what turns "I built a RAG system" into "I do AI engineering."

- **Golden dataset**: 200+ Q/A pairs over a realistic synthetic corpus (HR, security,
  finance, engineering SOPs across 3 tenants). LLM-generated, human-verified, with labeled
  relevant chunks and an expected-access-group field. Commit it.
- **Retrieval metrics**: Recall@k, MRR, nDCG@10, plus per-access-group breakdown.
- **Generation metrics**: faithfulness, answer relevance, citation precision/recall.
  Implement these yourself rather than importing RAGAS — the implementation is the portfolio.
- **Security metrics**: leak rate, over-block rate.
- **Ops metrics**: p50/p95 latency per pipeline stage, tokens/query, $/query.
- **The ablation table** — the centerpiece of the README:

  | Config | Recall@10 | nDCG@10 | Faithfulness | p95 | $/query |
  |---|---|---|---|---|---|
  | Baseline dense | | | | | |
  | + structure-aware chunking | | | | | |
  | + hybrid BM25 (RRF) | | | | | |
  | + cross-encoder rerank | | | | | |
  | + contextual retrieval | | | | | |
  | + agentic multi-hop | | | | | |

  Fill it with real numbers. Include a row where something *didn't* help and say so —
  honest negative results read as far more competent than an all-green table.
- **CI gate**: PR fails if nDCG@10 drops >2% or any red-team leak appears. Post the eval
  diff as a PR comment via GitHub Actions.

### 3.4 Platform & agentic surface

- **Multi-tenancy** end to end: `tenant_id` on every table, enforced by RLS, isolation
  proven by tests.
- **Async ingestion**: progress events, retries with backoff, dead-letter queue,
  idempotency keys, incremental reindex.
- **MCP server** exposing `search_knowledge_base`, `get_document`,
  `list_accessible_sources` — each scoped to the caller's principal token. Record a GIF of
  Claude Code querying your corpus and getting *denied* on a restricted doc. This is the
  most shareable 15 seconds of the whole project.
- **Admin console**: upload + ingest status, visual ACL editor, "preview as user X"
  (impersonation view showing exactly what a given principal can retrieve), audit log
  viewer, eval dashboard with run-over-run charts.
- **Observability**: OTel span per pipeline stage; Grafana dashboard screenshot in README.
- **Load test**: k6 script, published throughput/latency numbers under concurrency.

## 4. 12-week roadmap

Every phase ends with a git tag, a demoable state, and a README section. Commit daily —
the contribution graph and commit history are part of the portfolio.

**Phase 0 — Foundations (week 1)** → `v0.0` ✅ *complete*
Monorepo, Makefile, docker-compose (Postgres+pgvector, Redis, MinIO), Alembic, domain
models, CI skeleton (ruff/mypy/pytest), ADR-0001 through 0003.

Two amendments made during the build:

- **The synthetic corpus generator was dropped.** Choosing the GitLab handbook replaced it
  with a *declarative ACL derivation layer* (`corpus/acl_rules.yaml`, 19 rules,
  first-match-wins). Real structure beats generated structure, and the rules file is a
  better portfolio artifact than a generator script.
- **RLS moved forward from Phase 2 to Phase 0.** Retrofitting row-level security onto an
  existing data-access layer means touching every query path. The *plumbing* — principal
  context, transaction-local GUC, forced policies, the unprivileged app role — ships in the
  first two migrations. The ABAC policy *engine* still lands in Phase 2.

**Phase 1 — Baseline RAG (weeks 2–3)** → `v0.1` *(parity with the old project)*
Multi-format ingestion, structure-aware chunking, dual embedding backends (ONNX local +
OpenAI), dense search, cited answer generation, CLI. Integration tests with testcontainers.

**Phase 2 — Authorization core (weeks 4–5)** → `v0.2`
ABAC policy engine (compile `policies` rows into SQL predicates; enforce `region`,
`need_to_know_tags`, and `valid_until`, which Phase 0 stores but does not yet check),
chunk-level ACL overrides, filtered-ANN benchmark, audit hash-chain writer, red-team suite
v1 (100 attacks), CI security gate. **Write the filtered-ANN
recall blog post here — it's the most technically interesting thing you'll produce.**

**Phase 3 — Retrieval quality (weeks 6–7)** → `v0.3` *(centerpiece)*
Eval harness + golden dataset first, then hybrid+RRF, reranker, contextual retrieval,
query rewriting/HyDE/decomposition. Ablation table generated and committed. CI eval gate.

**Phase 4 — Agentic & MCP (weeks 8–9)** → `v0.4`
Planner/multi-hop loop with budgets, groundedness verifier, semantic cache, MCP server,
injection classifier, red-team suite v2 (250 attacks incl. indirect injection).

**Phase 5 — Platform (weeks 10–11)** → `v0.5`
Arq workers + DLQ + incremental reindex, OIDC auth (+ Keycloak profile), Next.js console
(chat, ACL editor, impersonation preview, eval dashboard, audit viewer), OTel + Grafana +
Langfuse, k6 load test.

**Phase 6 — Packaging (week 12)** → `v1.0` ✅ *complete*
README rewrite, architecture diagrams (Mermaid, in-repo), `THREAT_MODEL.md`, `CHANGELOG.md`,
3 writeups, Upwork case-study copy.

Two amendments:

- **Diagrams are Mermaid, not images.** They render on GitHub, diff as text, and cannot go
  stale the silent way a checked-in PNG does. Every block is parse- and render-checked
  under GitHub's strict security level.
- **The video and GIFs are scripted, not recorded.** They need a screen capture, which is
  the one deliverable that cannot be produced from a terminal. [`docs/DEMO_SCRIPT.md`](docs/DEMO_SCRIPT.md)
  is the shot list: exact commands, timings, and narration for a 4-minute walkthrough and
  three GIFs. **This is the only outstanding item in the plan.**

Packaging also turned up work rather than just describing it: re-running the ablation to
check the numbers before publishing them invalidated two of its own supporting claims, and
the generated findings prose is now computed from the results rather than typed in — it had
already drifted from the table directly above it.

Stretch (if ahead): Helm chart, fine-tuned domain reranker, GraphRAG entity layer, Slack bot.

## 6. Risks and cut order

| Risk | Mitigation |
|---|---|
| API cost over 3 months of eval runs | Local ONNX embeddings + reranker as default; cached LLM responses in the eval harness; contextual-retrieval outputs cached to disk |
| Scope creep across four pillars | Phase tags are hard gates — do not start phase N+1 until phase N is tagged and demoable |
| Filtered-ANN work rabbit-holes | Timebox to 4 days; if unsolved, ship the benchmark showing the problem and an honest ADR about the tradeoff taken |
| Synthetic corpus feels fake | Base it on real public SOPs/policies (NIST, GDPR texts, open handbooks like GitLab's) with synthetic ACLs layered on |
| Burnout at week 8 | Phase 3 (the centerpiece) lands at week 7 — if you stop there you already have a strong project |

**Cut in this order if time runs short:** Helm/k8s → Slack bot → OCR/multi-modal → Keycloak
(keep plain JWT) → Next.js console (keep a minimal one) → agentic multi-hop.

**Never cut:** eval harness, ablation table, red-team suite, README, ADRs.

## 8. Corpus selection

### Primary: The GitLab Handbook (verified, measured 2026-08-28)

`https://gitlab.com/gitlab-com/content-sites/handbook.git`

| Property | Value |
|---|---|
| Markdown files | 4,586 |
| Words / est. tokens | 6.13M / ~11.6M |
| Content size | 55 MB (`content/`), 333 MB full shallow clone |
| Format | Markdown + YAML frontmatter, Hugo/Docsy structure |
| License | **MIT** — usable, redistributable, no scraping needed |
| Ingest | `git clone --depth 1` — reproducible, versioned, diffable for incremental reindex tests |

This is the single best fit available. It is a **real company's actual internal operating
manual** — SOPs, policies, runbooks, org processes — which is exactly the document class the
system claims to serve. Everything else on the internet is either synthetic or the wrong genre.

**Why it fits the authorization pillar specifically.** The directory tree is already an
access-control model:

```
security/        424 files   → security-team, need-to-know
legal/           113 files   → legal, executives
finance/          74 files   → finance
people-group/     67 files   → people-ops (PII-heavy)
total-rewards/    26 files   → people-ops, compensation-committee   ← restricted
board-meetings/              → executives only                      ← restricted
ceo/                         → executives only                      ← restricted
people-policies/{france-sas,inc-usa,india-ltd,ireland-ltd}          ← jurisdiction-scoped
total-rewards/benefits/general-and-entity-benefits/ (17 countries)  ← jurisdiction-scoped
engineering/   1,243 files   → engineering (largest, general access)
support/         308 files   → support
sales/           187 files   → sales
```

Compensation, board material, legal, and employment notices are content that *plausibly should
be restricted* in a real company — so the demo is convincing rather than contrived. Frontmatter
gives you per-document metadata for free, and both `people-policies/` (four legal entities)
and `total-rewards/benefits/general-and-entity-benefits/` (17 countries) are partitioned by
jurisdiction, which exercises the ABAC `region` attribute rather than plain RBAC.

*(Corrected 2026-08-28: an earlier draft named `labor-and-employment-notices/` as the
jurisdiction-partitioned tree. It contains two files. The two trees above are the real axis.)*

**Sizing (so you know what you're signing up for):**
- ~14,500 chunks at 1000 tokens / 200 overlap.
- Embeddings: **$0.23** with `text-embedding-3-small`, **$1.51** with `3-large`, **$0** with local ONNX `bge-small`.
- Vector storage: 89 MB float32, 45 MB as pgvector `halfvec`.
- Contextual retrieval (the expensive step): ~$15–40 one-time with prompt caching on the parent
  doc. Cache results to disk and commit the cache manifest so re-runs are free.

Big enough to be real, small enough to re-index in minutes. Add a `CORPUS=small` seed profile
(one department, ~500 files) for fast iteration loops.

### Supporting corpora

**EnterpriseRAG-Bench** — `github.com/onyx-dot-app/EnterpriseRAG-Bench` (MIT). ~500k documents
across nine enterprise source types (Slack 275k, Gmail 120k, Linear, Drive, HubSpot, Fireflies,
GitHub, Jira, Confluence), **500 labeled questions** plus 100 metadata-dependent ones, and an
answer-evaluation harness. Deliberately seeded with misfiled docs, near-duplicates, and
conflicting information. Two uses: (a) it saves you hand-authoring most of the golden dataset,
(b) it is a *published leaderboard* — scoring on it turns your ablation table from
self-reported numbers into a comparable benchmark result. Individual 5,000-doc source slices
are downloadable, so start there. Layer your own synthetic ACLs on top.

**Enron corpus** — `cs.cmu.edu/~enron/`, 422 MB gzipped / 1.4 GB expanded, ~500k emails from
150 custodians. Use it for the security pillar only. Two reasons it is uniquely good there:
the folder-per-custodian layout encodes a **real organizational hierarchy**, so access groups
can be derived from actual reporting structure instead of invented; and it is the standard
corpus in RAG-leakage research — **LeakDojo** (ACL 2026 Findings,
`github.com/yeasen-z/LeakDojo`) benchmarks six extraction attacks in BEIR format against it.
Reusing their attack corpus means your red-team suite cites published methodology rather than
250 prompts you made up. Note: non-commercial research use, and it contains real PII — which is
actually the point, since it exercises the Presidio redaction path for real.

**Format variety** (Phase 1, to prove the parsers): SEC EDGAR 10-K filings (HTML + complex
financial tables), NIST SP 800-53 (long structured PDF), the GDPR text (deeply nested clause
hierarchy — good for structure-aware chunking), and a handful of scanned PDFs for the OCR path.
